# ATELIER GEM

A marketplace for individual loose gemstones, with an AI Jeweler Studio for designing a
custom piece around the stone a buyer chooses. Working name; change it in
`src/config/brand.ts`.

Build plan and live checklist: [PLAN.md](PLAN.md).

## Status: what works today

| Area | State |
|---|---|
| Design system, navigation, homepage, public and policy pages | Working |
| Gemstone catalogue, filters, search, cards (URL-driven, cursor pagination) | Built; shows an honest "not connected" state until Supabase is configured |
| Database schema, constraints, indexes, RLS, storage policies | Written and tested (24 security tests on PGlite); not yet applied to a hosted project |
| Auth, onboarding, listing wizard, verification, studio, quotes, checkout, messaging, admin | In progress (see PLAN.md) |

Nothing in the app pretends an integration works: when Supabase, Stripe, OpenAI or the
GIA service isn't configured, the relevant page says so.

## Requirements

- Node.js 20.9+ (developed on Node 24) and npm.
- A Supabase project (the free tier is enough for development).
- Later phases: a Stripe account in **test mode**, an OpenAI API key.

## Database setup (Supabase)

1. Create a project at supabase.com. In **Project Settings → API**, copy the project URL,
   the `anon` key and the `service_role` key into `.env.local`.
2. Apply the migrations in `supabase/migrations/` **in filename order**, either:
   - with the Supabase CLI: `npx supabase link --project-ref <ref>` then `npx supabase db push`, or
   - by pasting each file into the SQL editor, oldest first.
3. In **Authentication → URL configuration**, set the site URL and add
   `http://localhost:3000/auth/callback` as a redirect URL.
4. Make yourself an administrator (SQL editor, as the project owner):
   ```sql
   insert into public.user_capabilities (user_id, capability, approval_status)
   select id, 'admin', 'approved' from auth.users where email = 'you@example.com'
   on conflict (user_id, capability) do update set approval_status = 'approved';
   ```

The service-role key bypasses row level security. It is read only in server modules
(`src/lib/env.server.ts`, guarded by `server-only`) and must never be exposed to the browser.

## Storage

The storage migration creates four buckets: `listing-photos` (public read, seller-only
upload), `listing-documents` (private: seller and administrators), `design-assets`
(private to the design owner) and `avatars`. Object names are generated by the server;
user-supplied file names are never used.

## Project layout

```
src/app/            routes (App Router; cacheComponents on — dynamic data renders in <Suspense>)
src/components/     ui primitives, site chrome, gemstone components, brand artwork
src/lib/domain/     pure logic: money (integer minor units), search params, vocabularies
src/lib/services/   server-side business logic (one service per domain)
src/content/        policy page drafts (not legally reviewed)
supabase/migrations SQL schema, RLS and storage policies
tests/db/           PGlite harness + RLS tests
```
